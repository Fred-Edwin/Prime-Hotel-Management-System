**What was built:**
- `lib/actingAs.ts` (new) — `ADMIN_ACTING_AS_COOKIE`, `ActingAsRole`/`ActingAsLocation`/`ActingAsState` types, `normalizeActingAs()`/`parseActingAsCookie()`. Edge-safe (no Node-only imports), shared by `proxy.ts` and `lib/auth.ts`.
- `lib/auth.ts` — new `getActingContext()`: resolves a real staff session unchanged, or an admin's `admin_acting_as` cookie (re-validated server-side, never trusted at face value), or `null` otherwise. Returns `{ location, actingAs, isStoreManager, user }` shaped so every existing consumer can branch on `.location`/`.isStoreManager` exactly as before.
- `app/api/admin/acting-as/route.ts` (new) — `GET` returns current acting-mode state; `POST` sets (8-hour httpOnly cookie) or clears it (`role: null`).
- `proxy.ts` — `isStaffRoute && isAdmin` now allows through if a valid `admin_acting_as` cookie is present (cheap shape-parse, no DB call); otherwise redirects to `/dashboard` as before.
- `app/(staff)/layout.tsx`, `app/(staff)/entry/page.tsx`, `app/(staff)/orders/page.tsx`, `app/(staff)/store/page.tsx` — all guards swapped from `getCurrentUser()` to `getActingContext()`. `store/page.tsx`'s extra check now also accepts admin acting as Store Manager.
- `app/api/stock-entries/route.ts` — GET/POST/PUT guards swapped; PUT's three-way dispatch (`putCanteenField`/`putStoreManagerField`/`putCashierField`) now keys off the *effective* location/role from `getActingContext()` instead of raw session fields; the two hardcoded `p_location: "restaurant"` literals are gone, replaced by the derived location. - `app/api/orders/route.ts` — GET/POST guards swapped; POST writes an `order.admin_acting_as_create` audit entry when acting.
- `app/api/ingredient-entries/route.ts` — `requireStoreManager()` now takes the resolved `ActingContext` instead of the raw user row; GET/POST/PUT guards swapped; POST/PUT write `ingredient_entry.admin_acting_as_create`/`_edit` audit entries when acting.
- `components/RoleLocationBadge/*` — new `"acting"` variant (dashed border, `--color-status-warning`/`--color-status-warning-bg` tokens — reused existing tokens, no new colors invented).
- `app/(admin)/AdminShell.tsx` + `.module.css` — wired the previously-unwired "Add Entry" top-bar stub, plus a new sidebar "Act as staff" button (per direct client request for a sidebar dropdown/picker), both opening the same two-step `Modal`: pick Cashier or Store Manager, then (Cashier only) pick Restaurant/Canteen via the existing `PeriodToggle` component, then `POST /api/admin/acting-as` and navigate into `/entry` or `/store`.

**Challenges faced:**
- The most valuable finding of the whole piece of work came from exploration, not implementation: RLS on `stock_entries`/`ingredient_entries`/`orders`/`order_items` already had an unconditional `is_admin()` bypass on every relevant policy, so the entire feature reduced to an application-layer guard change — no migration, no new column, no new RLS policy. This was verified by reading migration files directly (`20260710110003_rls_and_functions.sql` and the policies that superseded it), not assumed.
- `app/api/stock-entries/route.ts`'s PUT dispatch had two hardcoded `p_location: "restaurant"` string literals that were silently correct only because of dispatch order (canteen branches first) — these would have broken invisibly for an admin acting as canteen if left as-is. Found by careful reading during the plan phase, fixed by threading the resolved `ctx.location` through instead.
- A mid-session correction: the original plan's UI sketch (top-bar "Add Entry" only) was revised after the client explicitly asked for a sidebar-based role dropdown instead — both entry points now open the same modal, so neither was thrown away.
- **Curl verification caught a real bug of this feature's own making**: the batch-save `POST` audit calls (`stock_entry.admin_acting_as_create`, `ingredient_entry.admin_acting_as_create`) passed `entry_date` (e.g. `"2026-07-25"`) as `writeAuditLog`'s `targetId`, but `audit_log.target_id` is a not-null `uuid` column — every batch-save audit call silently failed server-side (logged, but the save itself still succeeded, since audit failure doesn't roll back the write). Fixed by auditing against the first saved row's own `id` instead, with `entry_date` still recorded in `changes`. Confirmed fixed by re-running the same curl call and checking the dev server log had no `[audit] write_audit_log failed` line, then confirming the entry via `GET /api/audit-log`.
- **Curl verification also surfaced a pre-existing, unrelated bug**: `POST /api/orders` returns 500 (`PGRST203`, "Could not choose the best candidate function") whenever `customer_id` is omitted from the request body — Postgres has two overloaded `create_order()` signatures (with and without `p_customer_id`) and PostgREST can't disambiguate which to call. Confirmed this is **not** caused by this feature's changes: reproduced the identical error logging in as Anne (real canteen staff, no acting-mode involved) with the same omitted-`customer_id` payload. Worked around it for this session's verification by always passing a real `customer_id`; the underlying fix (rename/consolidate the two `create_order` overloads in a migration) is a separate piece of work, not touched here — flagged to the human as a real, currently-live bug affecting the *existing* orders flow for real staff, not something this feature introduced.
- Added one `console.error("[orders] create_order failed", error)` line in `app/api/orders/route.ts` (matching the existing precedent in `app/api/staff/route.ts`) — `describeSaveError()`'s fallback path had no server-side logging at all, which is how the pre-existing `create_order` bug above went undiagnosed until this session; kept as a small, permanent improvement rather than reverted, since it's consistent with existing codebase conventions and meaningfully aids future debugging.
